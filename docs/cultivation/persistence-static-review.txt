Blocking finding PERSIST-01: failed fallback read exports fresh placeholder
  Trigger: the cultivation key does not exist; its getItem succeeds with null;
  the subsequent read of HearthRTS.KEY throws (e.g. key-scoped read failure).
  At48 readCompleted becomes true immediately after only the first read.
  At51 the legacy read is outside its inner parsing try. The outer catch at59
  therefore sets rejected=null, unreadableSave=false, game=new HearthRTS.Camp(),
  blocked=true and paused=true. ui at484 disables current export only when
  unreadableSave is true; handler528 consequently exports envelope() around the
  fresh placeholder instead of recognizing that the former opening is unreadable.
  Nothing overwrites the old key, but the visible current export is not a copy of
  the unavailable user's opening and can be mistaken for recovery of that state.

  Smallest fix: distinguish completion of all selected initialization reads from
  completion of the new-key read. On absent cultivation slot, mark a thrown
  legacy-key read as unreadableSave and disable current export until a successful
  reload. Do not downgrade it to an absent/invalid optional legacy source. Keep
  fresh creation available when BOTH reads succeed and both keys are absent.

  Required bounded Spark regression: getItem(newKey) returns its actual null;
  only getItem(oldKey) throws. Assert no key write, blocked orders, persistent
  unreadable warning, current export disabled, original key unchanged. Remove
  fault/reload and verify actual existing v6 opening is selected and its raw
  source export is byte-exact. No invented gameplay state is needed: use the
  browser's earned/exported v6 source from the current harness setup.
