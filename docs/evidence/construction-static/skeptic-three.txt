1. Array identity: exact static admission trace
Take a legitimate v6 active, unpicked outpost S funded by b0, with no assigned worker, no cargo, no staged material and zero work. Its sources are 60 wood and 20 stone. Actual b0 stock may be exactly 60 wood and 20 stone; a normal canonical camp can earn this from the starting 20 wood and 10 stone by gathering 40 wood and 10 stone. Keep deposits, delivered, stock, and all other canonical state consistent. Change only each S source row's storeId from the string "b0" to the JSON array ["b0"].

At engine lines 70 and 76, reserved is an ordinary object containing an own b0 vector. Bracket lookup reserved[p.storeId] converts the single-element array to the property key "b0". There is no type check, own-key check, or strict live-store membership check for p.storeId. The duplicate-key expression p.storeId + ':' + p.resource also coerces to b0:wood or b0:stone, so these two distinct resource rows do not fail uniqueness. Each positive integral amount is added to reserved.b0.

Line 79 checks the canonical recipe through resource and amount, independently of the store identity's type. Line 84 observes reserved.b0 = 60 wood and 20 stone, which is backed by the actual stock. Zero staged/released/returned vectors, empty origins, and idle workers satisfy the remaining construction checks. The old paid-reservation validators at lines 45–49 do not inspect these physical-source rows; physical sites are explicitly omitted from legacy obligations. validReclaim/canonicalReason at lines 97–160 conserve inventory and paid capital, but do not impose another strict current-source identity check. Source reservations are not additional physical inventory, and these physical unfinished sites are not spent capital, so those checks remain satisfied.

The constructor at line 186 first validates the supplied state, then structured-clones it as current v6 data, and validates again. Cloning preserves the array. Nothing in this constructor converts it to a string or rejects it. Thus the malformed input is admitted and remains malformed.

stores() line 297 counts a construction reservation only when p.storeId === b.id. ["b0"] !== "b0", so S's reservations are omitted from b0.reserved and b0.available reports the whole 60 wood and 20 stone as free. economy(), canPay(), funding(), and planSupply() use this availability at lines 303–325, 412, and 206–208.

For an otherwise clear, visible, connected second outpost location R, build() passes its funding check and appends a new physical ledger row with ordinary string storeId "b0" at lines 418–425. Selecting [] is expressly accepted by the engine; no worker movement or pickup is needed for the failure. An example consistent with the canonical western map is S at 11,15 and R at 11,11, subject to the normal workers being outside those footprints. Both sites have access to the hearth. No new material is added or spent by either reservation.

build() has no final valid() check and returns R's new id. On the next validation, line 76 counts both the coerced S reservation and the genuine R reservation against reserved.b0, yielding 120 wood and 40 stone against actual 60 wood and 20 stone. Line 84 returns false. serialize() at line 461 still emits JSON, while new Camp(parsedSerialization) rejects immediately at line 186. This is the concrete persistence failure supported by the inspected engine. Controller autosave behavior and durable-backup handling were not inspected and cannot be claimed here.

The malformed S cannot autonomously pick its purported sources: supplyTargets() line 210 and pickupSupply() line 224 require strict building id equality. Its builder therefore cannot materialize a second real load from the array identity. The demonstrated effect is lost reservation authority, a stalled original site, competing use of those goods, and a subsequently invalid live/exported state, not direct duplication of physical inventory at the malformed pickup.

3. Inherited string keys: exact writes and limits
The accumulator constructed by Object.fromEntries at line 70 has the ordinary Object.prototype. With source storeId "toString", line 76 sees the inherited Object.prototype.toString function, which is truthy. The update reserved[p.storeId][p.resource] += p.amount writes wood/stone properties onto that shared function object. In a clean realm each missing property starts undefined, so undefined + a positive number produces NaN. It does not write the number 60 or 20 there.

With source storeId "__proto__", the same lookup returns Object.prototype through the inherited accessor. The update writes Object.prototype.wood and Object.prototype.stone; again the values become NaN in a clean realm. Resource membership at line 76 restricts the property written to wood, stone, or food, and canonical recipe checks prevent positive food rows for these building recipes. This path does not provide arbitrary property names, arbitrary values, function replacement, or demonstrated code execution.

Object.entries(reserved) at line 84 enumerates only own store keys, so it never validates these inherited reservation targets. Canonical world totals remain unchanged, and every normal resource vector has its own wood/stone/food values. A reserved-only site with these inherited source IDs can therefore pass even without 60 wood and 20 stone in an actual store. No string-to-live-building guard later rejects the source IDs during admission. Runtime strict equality again omits these rows from availability and prevents an actual pickup from the nonexistent store.

The mutation occurs inside validConstruction, before the later complete validReclaim checks. Accordingly, even a state ultimately rejected by a later check can already have modified the inherited function or Object.prototype in this realm. new Camp validates before cloning, so the constructor does not isolate that side effect. These effects are a concrete validator purity/realm pollution defect; broader consequences outside this engine were not established by the permitted review.

4. Planned-pickup guard
Line 90 uses !s.storage.stores[p.storeId] without a type/own-key/live-store check. With a legitimate active site/order, phase supplyPickup, zero cargo, no successor or dropoff, and a recipe resource, a planned storeId ["b0"], "toString", or "__proto__" can satisfy that lookup. This branch does not itself perform the += write. On pickup, line 224's strict live-store lookup finds no matching store, so line 225 calls start() instead of debiting inventory. A valid source ledger may thereby recover to a new valid plan; a malformed source ledger remains stalled. This is still an admission/schema defect, but it is not an independently established goods-duplication path.

5. Minimal guard recommendation, without an authored fix
Use one explicit current-store identity predicate before dictionary access or arithmetic. Require typeof storeId === 'string', strict membership in the ids of buildings satisfying isStore, and an own entry in s.storage.stores. For the reservation accumulator, require its own corresponding entry before addition (or construct a null-prototype accumulator after strict live identity checks). Apply this to each construction sources row at line 76 and each supplyPickup plan at line 90. Type alone does not reject inherited string names; an own-property lookup alone still coerces arrays, so the protections need to be combined or supplied by equivalent strict live-id membership.

Do not apply the live-store predicate to delivered origin snapshots or carried historical origins: retirement is allowed by the contract. Do not demand that a planned pickup still have a positive matching current source row merely to fix C02: another worker can legitimately consume the last reservation while this worker retains a pending pickup plan until its next tick. Retain that race handling at line 225.

The typed live-store guard is small and directly addresses the confirmed mismatch while preserving legitimate historical origin custody.
