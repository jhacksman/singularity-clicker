Q1. Queued-close assertions do not establish that the replacement controller survives the old close event.

The case at campaign-navigation.cjs:372–376 opens the real completion modal, synchronously activates Stay and the underlying event-action control, waits for readyNative, then waits for a zero-delay timer. It checks modal.open, mount count two, an enabled rendered forward button, and unchanged source bytes. The native setup observes pagehide/pageshow but does not observe the modal's close event. readyNative at 241–244 awaits the stored controller.ready promise without checking its result and then checks rendered status DOM.

The widget's dispose implementation at browser.js:138 removes click/storage listeners and invalidates pending refreshes. It leaves the rendered DOM, latest snapshot, already-resolved ready promise, and external mount telemetry intact. An enabled button therefore does not establish that the controller still handles it.

Concrete conditional regression witness: remove the host close handler's !modal.open guard, and let the replacement refresh/render finish before the old queued close handler runs. The old handler then disposes the replacement and resets dialogPauses while the new modal remains open. Every current queued-close assertion can still pass: DOM and ready are retained, mount count remains two, and source bytes remain unchanged. The completed Cave fixture also masks loss of the host pause flag because Cave advance() returns immediately when complete. The current source correctly retains the guard at view.js:139; this is a missing regression oracle, not a claim that today's guarded handler disposes the replacement.

Disproof limit: if the old close event runs before the replacement finishes refreshing, disposed refresh returns null and no status DOM is rendered; the existing test can fail in that ordering. It therefore provides some protection. It does not force or observe the relevant event ordering, and the zero-delay timer is not proof that the specific old close event ran. The concern is a permitted false-pass interleaving and insufficient liveness evidence, not an assertion that the current browser always follows that interleaving.

Bounded correction: install a read-only close-event observer before the synchronous Stay/reopen operation and await the actual old close event. Afterward require a fresh externally observable operation from the replacement controller, such as a recognized source-key storage change followed by a newly identified snapshot/export, or a real native action with a fresh expected result. Merely awaiting the original ready promise, inspecting its existing snapshot, or checking an enabled DOM control is insufficient. Keep the modal-open and mount-count assertions; additionally check focus remains in the open modal and an applicable host pause guard. Unchanged completed-Cave bytes alone cannot prove that pause guard. No current host behavior change is needed to address this evidence gap.
