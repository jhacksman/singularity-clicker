Verdict
One new Medium static blocker: optional certification overlooks fractional
reservation-source amounts. A previously accepted v4 camp can be certified and
adopted as v5, then an ordinary Cancel creates a v5 save rejected on refresh.
The two reported first-draft defects are corrected in this frozen candidate.
No separate canonical minting counterexample found under the two equations.
This is source reasoning, not executed reproduction or release clearance.

S1 — Medium, confirmed static admission/roundtrip defect
Relevant engine.js lines: 38-45, 59, 69, 90-96, 102, 143, 338-341.
Relevant view.js lines: 33, 315-319.

Attempted disproof:
- Legacy valid() checks each reservation source with n(amount), requiring a
  finite positive bounded number, not an integer (41,43).
- Its per-resource reservation sums must equal the canonical bill (45), but
  sums can be integral while named-store components are fractional.
- canonicalReason checks integer stores, transferred metrics and PAYMENT source
  amounts (69). It does not inspect RESERVATION source amounts.
- paymentReason's reservation comparison (84-85) runs only for a present payment.
  Missing payments are explicitly supported by the contract and implementation.
- v5 validReclaim invokes the same canonicalReason and therefore has no later
  reservation-integrality guard. Compacting payments does not repair reservations.
These checks do not reject the witness.

Concrete source-plausible witness; this is an edited supported-reader input,
not a claim that an ordinary historical play session generates half units:
1. Start from the ordinary v4 shape with canonical deposits, b0 hearth, four
   u0..u3 empty idle actors, tools=false, knapping=null, no transfer jobs.
2. Add b1 completed outpost at (0,0), work=24, cost={wood:60,stone:20}; add b2
   unfinished outpost at (4,0), work=0, with the same canonical cost. nextId=3.
3. Set d0.amount=0, d1.amount=0, d4.amount=176, d2.amount=30; retain all other
   canonical initial/remaining source fields. This consumes 100W and 30S.
4. stock={wood:0,stone:0,food:0}; spent={wood:120,stone:40,food:0};
   delivered={wood:100,stone:30,food:0}; depleted=2; complete=false.
5. storage: version=1, nextId=1, transferred=zero vector, transfers=[],
   payments=[], stores.b0=zero vector, stores.b1=zero vector. Its only reservation:
   b2.sources=[
     {storeId:'b0',resource:'wood',amount:0.5},
     {storeId:'b1',resource:'wood',amount:59.5},
     {storeId:'b0',resource:'stone',amount:20}
   ]. Ordinary bounded time/seen/actor fields are unchanged.

The two equations independently balance:
  wood: 296 wild + 0 stored + 0 cargo + 120 spent = 416;
  stone: 180 wild + 0 stored + 0 cargo + 40 spent = 220;
  food: 225 wild + 0 stored + 0 cargo + 0 spent = 225.
  paid: two outposts = 120W40S, exactly spent.
Legacy valid() accepts the reservation sum; certifyLegacy returns ok; constructor
adopts two full claims and its final v5 valid() still passes by the same chain.

Call cancel('b2'). Lines 339-341 refund to actual named sources and remove b2.
Result: b0 contains 0.5W20S, b1 contains 59.5W, stock=60W20S,
spent=60W20S. Aggregate matter is conserved, but vector(store) now fails line69.
serialize/save has no valid() gate (view33), so the ordinary UI cancellation
saves this state. Reload rejects it as v5, pauses a fallback world, and offers
the rejected original for export. An outgoing import is also blocked because
line318 explicitly verifies the now-invalid outgoing camp.

Severity boundary: this requires a fractional imported/edited legacy reservation;
it is not evidence that canonical old gameplay generated fractional goods. It is
nevertheless a concrete violation of the promised canonical-integer certificate
and failure-preserves-play boundary. Exact original import/startup backups reduce
irrecoverability; they do not make the adopted current camp roundtrip valid.

Minimal correction direction for sole fixer:
Apply canonical bounded integer checking to every refundable reservation source
as well as payment sources. For v3/v4 this must fail OPTIONAL certification and
retain the accepted legacy compatibility camp, not reject formerly playable raw
input. The same condition should reject this malformed claim-bearing v5 input.
Do not round source amounts, invent payment rows, change named refund origins,
or tighten the legacy reader indiscriminately.

First-draft findings independently checked
FRESH CERTIFICATION — fixed statically. The saved initial draft certifies fresh()
before it has storage even though fresh.version=4. Candidate line143 first runs
migrateStorage(), then uses a clone of that complete fresh state for certification
when no source argument exists. The supplied legacy source remains the certificate
basis for actual v1-v4 inputs. No missing-storage failure remains on this path.

STORAGE NEXT ID — fixed statically. Candidate line69 requires integer(nextId),
which includes <10000000, plus >=1. A legacy v3/v4 source accepted by old valid()
with an out-of-range transfer counter now fails optional certification rather
than receiving a certificate and failing final v5 admission. Constructor keeps
the version4 compatibility state and reclaimIssue. This deliberately preserves
the prior reader's broader acceptance rather than silently widening v5 limits.

Other attacked paths; no additional concrete blocker found

  143). New claim/retirement/cargo authority is generated only by adoption, not
  inherited from unknown old-schema fields. Old-schema reclaim orders/phases
