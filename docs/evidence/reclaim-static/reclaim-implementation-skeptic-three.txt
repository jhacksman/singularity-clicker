RI-S3-01 — previously offered recovery source can be lost on successful import
Severity: Medium, bounded recovery-data preservation failure; static confidence
high. This is not ordinary verified live-camp loss and not a runtime reproduction.

Witness using three distinct raw strings A, B and C:
1. KEY initially contains A that this reader cannot open (for example a future
   payload). Startup catches the load failure, retains rejected=A, blocks saving
   and offers A through Journey export. No before-v5 backup was made because
   candidate construction failed before preserveBeforeWrite.
2. Another tab changes KEY to B, or deletes it. The existing storage listener
   pauses/blocks but does not change rejected=A. Journey still offers A. A now
   need not exist in any durable key; this document retains its recovery copy.
3. User imports supported C and confirms replacement after storage is available.
   Import's outgoing expression returns null because rejected!==null. It backs
   up C and current prior=B (or no stored record if KEY is null), but never A.
4. After successful KEY commit, the success branch clears rejected. A loses its
   last application-held recovery copy. The previous error/export path promised
   that copy, yet successful recovery import does not retain it.

Source: view startup catch (line29 in the frozen file), export312, import318-319,
storage handler321. The important source facts are rejected=originalRaw in catch;
outgoing=rejected===null&&!unreadableSave?game.serialize():null; only prior is
added as stored-before-import-v5; and success sets rejected=null.

Disproof attempted: ordinary A still in KEY is protected by the prior backup;
an already-created before-v5 copy also protects A; a failed import retains the
in-memory rejected value. Those facts narrow the witness, but do not cover a
changed/deleted KEY after startup rejection with no earlier copy. A can also be
a supported source whose startup preservation failed, rather than necessarily
an unsupported save. No fabricated engine state or material exploit is needed.

Bounded correction: preserve any known rejected/recovery raw A before successful
replacement, in addition to current prior B and verified outgoing LIVE state.
Use the existing collision-safe stored-before-import-v5 family for distinct raw
sources; do not serialize the fresh fallback as a guessed outgoing camp. Include
empty-string A by testing against null rather than truthiness. Root acknowledged
this scope and proposed that correction; I have not reviewed a changed source.
Needed browser regression: first observe original A export, change/delete KEY,
import C, then verify independently retained exact A/B/C copies and current C.
Also inject failure while preserving A and require no candidate adoption or
loss of the previous recovery export. Root owns correction and separate review.

Startup and ordinary import checks that held
preserveBeforeWrite plans collision-safe records without replacing distinct
bytes, checks expected KEY before writes and again before main commit, rechecks
each intended backup slot, then writes KEY last. A read/backup/main-write throw
prevents the following adoption assignment; earlier successful backups may
remain without being called a committed import.

Startup constructs incoming privately, preserves an old source and writes its
serialization before game=incoming. Catch retains originalRaw as rejected and
blocked prevents the final save from overwriting it. Journey reads rejected
before serializing fallback. When the first KEY read fails, unreadableSave blocks
export and save, rather than pretending a fresh camp is the original source.

Import serializes the current live game after file reading/confirmation, validates
that outgoing representation, and backs it up separately from incoming raw text.
It also preserves exact prior KEY when different from the live serialization.
Thus a live camp newer than autosave is not replaced by the older disk snapshot
in its outgoing record. Normal preservation/write failure leaves game unchanged,
pauses/blocks, and does not execute the success message or dialog-close branch.
Import parsing/candidate construction precedes these writes. Rejected-source
retention in RI-S3-01 is the uncovered additional input, not a failure of this
ordinary verified outgoing path.
