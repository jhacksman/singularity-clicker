Disproof reasoning
1. Host src/view.js:137 opens the real dialog with showModal(); src/shell.html:60 supplies the dialog and #modal-close. completion() at view.js:152 places #replay last after the helper and Stay button. The host keydown handler does not implement Tab wrapping. The widget uses ordinary DOM controls and only restores focus during its own rendering; it has no Tab trap. The test therefore asserts a browser boundary behavior that the application does not implement itself.

2. The HTML Standard distinguishes document modality from browser controls. showModal makes the connected document outside the dialog inert. Sequential focus navigation step 8 permits transfer to the user agent's own controls when there is no next document candidate; it does not require immediate DOM wrap. This supplies a concrete counterexplanation to the claimed product failure, not proof of what this run did. Sources: https://html.spec.whatwg.org/multipage/interaction.html#modal-dialogs-and-inert-subtrees and https://html.spec.whatwg.org/multipage/interaction.html#sequential-focus-navigation (read 2026-10-04). The directly relevant WHATWG discussion also documents this distinction: https://github.com/whatwg/html/issues/8339 . No WCAG or cross-platform accessibility compliance conclusion is made here.

3. At campaign-navigation.cjs:307–310 the internal forward/backward keyboard order and visible focus outline assertions completed before the failure. Line 311 explicitly focuses #replay, presses Tab, then checks only document.activeElement.id against 'modal-close'. Its actual '' does not identify a tag, ancestor, navigation action, or document focus state. The widget has legitimate ID-less controls inside the dialog. BODY/HTML or another ID-less node would also produce this string. The catch at lines 483–487 records URL, body text, lifecycle, storage calls, and mount count, not activeElement identity, containment, or document.hasFocus(). Body text containing background content does not prove background focus or operability.

4. The screenshot shows the completion dialog over a dimmed/blurred backdrop. It does not show browser chrome and does not establish which element has focus. No observed background interactive focus, activation, unintended navigation, or page error appears in the returned diagnostic. Conversely, the screenshot and empty pageErrors array cannot establish that focus behavior was correct.

This artifact alone cannot choose between all actual destinations.
