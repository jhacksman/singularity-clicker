Platform counterevidence

The WHATWG HTML Standard's sequential focus navigation algorithm permits the browser to transfer focus to its own controls when navigation reaches the top-level boundary. Native modal behavior separately makes the document's other nodes inert. It therefore does not follow that one Tab from the last dialog control must immediately focus its first control. Sources checked during this review:
https://html.spec.whatwg.org/multipage/interaction.html#sequential-focus-navigation
https://html.spec.whatwg.org/multipage/interaction.html#modal-dialogs-and-inert-subtrees

This is a standards-based counterexample to the oracle's universal requirement, not evidence that Navigation026 actually moved focus into browser chrome. The failure lacks activeElement.tagName, navigation-action/focus attributes, modal containment, document.hasFocus(), and focus/blur events. An element with no ID inside the dialog, a document-level focus representation, or loss of document focus cannot be distinguished from the recorded ''. Do not label BODY, browser chrome, or any outside control as the observed destination.

Disproof limits

- An empty ID does not prove background focus leakage, but also does not prove correct containment or useful keyboard recovery.
- Passing adjacent-control Tab navigation and focus-visible styling supports some keyboard behavior; it does not close end-of-dialog traversal, reverse traversal, Escape, or actual action reachability.
- Native showModal source and the inertness contract argue against inventing a custom trap merely to satisfy a browser-specific assertion. They do not replace browser evidence that the native behavior works in this built page.
- If stronger diagnostics later identify a focusable background game control receiving focus or an inability to reach/activate dialog controls, that is a separate concrete product candidate requiring fresh triage. It should not be pre-dismissed as browser chrome.

Record at least: active tag/id and navigation-action/focus attributes; whether it is inside the modal; modal.open and native :modal status; document.hasFocus(); and a short focusin/focusout/window-focus/window-blur trace. Capture the failure-time snapshot at the failing step, rather than relying only on a later screenshot/catch read.

The revised oracle should reject any observed focus on a background interactive game control, retain actual in-dialog forward/reverse traversal checks, and demonstrate bounded keyboard return/re-entry and activation of a native dialog control. Distinguish a recorded document-focus departure from merely seeing an empty ID. Do not change the expected value to '' or accept any missing ID unconditionally. A separate background focusability probe can support native inertness, but should be labeled separately from the actual keyboard traversal and must not manufacture focus recovery before that recovery is observed.
