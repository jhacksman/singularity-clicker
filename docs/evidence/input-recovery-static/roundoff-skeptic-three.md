# Roundoff save/reload review — independent skeptic 3

**Verdict: confirmed High release-priority reload blocker in ordinary play.** Static disproof attempt against immutable commit `f93798b3`, `src/hearth-rts/engine.js` and `view.js`. No app edits, runtime, parser, tests, lint, or browser execution were performed on M6. No other skeptic report was read. The only file authored for this review is this report.

The candidate is an engine-generated invalid save, not malformed imported input. Completing the paid knapping project sets `tools=true` at engine line 193. A subsequent ordinary gather order invokes `start`, which sets work to zero at line 139 and enters extraction at line 149. Walking consumes simulation ticks without extraction at line 182, so count the following sequence from the first extraction tick after arrival. Choose a deposit with more than two items remaining and an initially empty carrier. The browser invokes the engine with exactly `.1` at view line 87; variable animation-frame timing therefore does not change these individual arithmetic steps.

**Independent arithmetic check.** The decimal literals are binary64 values. In exact rational form, `.1` is `3602879701896397 / 2^55` and `.45` is `8106479329266893 / 2^54`. Starting from zero, five successive `.1` additions reach `.5`; subtracting the tools interval gives `900719925474099 / 2^54`, displayed as `0.04999999999999999`. Four further rounded additions give the following states:

| Extraction tick | Work after addition, before any extraction | Work after extraction | Cargo |
| --- | --- | --- | --- |
| 5 | `0.5` | `0.04999999999999999` | 1 |
| 6 | `0.15` | unchanged | 1 |
| 7 | `0.25` | unchanged | 1 |
| 8 | the binary64 value displayed as `0.35`, slightly below exact 0.35 | unchanged | 1 |
| 9 | `0.44999999999999996` | `-5.551115123125783e-17` | 2 |

The tick-eight addition rounds to `6305039478318694 / 2^54`; tick nine rounds to `8106479329266892 / 2^54`. Each tie rounds to the even significand. The tick-nine value is exactly one `2^-54` below the `.45` literal. Engine line 192 admits extraction because it compares `u.work + .00001 >= interval`, then subtracts the interval without clamping or normalization. The result is exactly `-2^-54`, a nonzero negative number, not negative zero. This is a manual binary64 derivation, not an executed numerical experiment.

**Attempted reset/reachability disproof.** At cargo two with deposit stock remaining, neither the full-load nor exhausted-deposit branch calls `home`; the actor stays in extraction with its negative work. The next simulation tick would add `.1` and make work positive again. This limits the bad state to a transient window during continuous play, but does not exclude saving that window. `start` resets work only when invoked; ordinary uninterrupted extraction does not invoke it between these two items. The completed project retains `tools=true`, and no tick-end normalization occurs. Both the original paid tool progression and the fresh extraction starting at work zero are reachable without manipulating save fields.

**Persistence and rejection.** Engine lines 18 and 29 require every unit's work to be finite and at least zero. This check precedes the legacy-version early return at line 30, so it applies to all supported versions. The constructor rejects the negative value at line 50 before adoption. Engine line 198 serializes `this.s` directly. JSON serialization preserves this finite nonzero negative value; it is not rounded to zero by UI formatting.

View line 10 writes that serialized state without validation or numerical normalization. The Pause button at line 32 freezes progression and calls `save` immediately. A click after the ninth extraction tick and before the tenth thus preserves the invalid value indefinitely. Visibility change and pagehide also call `save` at line 86; periodic saving at line 87 is another possible capture route whose alignment is not needed for this proof. Opening the Journey dialog also stops simulation through line 87's dialog condition, so later periodic saving can capture a frozen bad value. On reload, view line 6 calls `new Camp(state)`, catches its rejection, retains the original raw slot in `rejected`, substitutes a fresh in-memory camp, and sets blocked/paused. Ordinary play cannot resume from the saved camp through the app.

**Counterevidence and severity limits.** Continuous simulation can repair this tiny residual on the next tick and a later good save can overwrite it. The source does not establish that every post-tools save fails or that the two-second autosave always hits the bad tick. It establishes a real intermediate state that normal Pause or pagehide can persist. The raw saved camp remains available for export, and the simulation has not destroyed its physical inventory. Therefore the impact is loss of normal reload/resume with external repair/recovery required, not irreversible deletion or resource corruption. High is justified by the stated requirement that normal earned camps remain saveable and reloadable; the arithmetic magnitude does not reduce that user-visible failure to Low.

**Existing evidence does not disprove it.** At `f93798b3`, `tests/hearth-rts.test.cjs` lines 37–41 tests upgraded extraction for two seconds and checks output, capacity, and resource conservation. It does not validate or reload at each intermediate extraction tick. Its knapping round-trip at lines 33–35 concerns project progress and completion, not the negative gather-work window. The storage suite's Stop/Move/Gather transfer round-trips at lines 233–237 use the expansion fixture without crafting the tool upgrade. In `tests/browser/hearth-rts.cjs`, lines 24–25 complete tools and gather food, then Stop and wait until all cargo is returned and actors idle. The later reload at line 28 therefore occurs after normal receipt/start has reset work, rather than during the candidate window.

The inspected Spark021 log reports 79 unit tests passing and a fresh RTS browser flow passing. Its later recovery-browser timeout is unrelated evidence, not this finding's reproduction. Those results are compatible with the missing intermediate-state coverage above; they do not close the candidate. A targeted Spark reproduction remains required.

**Attribution caveat.** Baseline delivery commit `0cf94678a155eb24c7a15713eee5b3cfefea35b7` already contains the same unclamped extraction arithmetic at engine line 66, strict work validation at line 26, and direct serialization at line 72. This is a pre-existing latent defect exposed during the storage/recovery review, not evidence that the storage increment introduced the floating-point subtraction. Its effect still blocks the increment's normal-save recovery claim.

No fix or execution result is claimed. The decisive Spark check is an ordinarily earned tool upgrade followed by a gather task, validating and round-tripping each extraction tick, plus an actual Pause/reload during the negative-work window. Existing snapshots with the tiny negative work also require an explicit recovery disposition; preventing new negatives alone does not demonstrate that old blocked saves are recoverable.
