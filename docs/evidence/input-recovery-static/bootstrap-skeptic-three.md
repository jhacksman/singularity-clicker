**P-02: recovery repeats the failing operation without protection.** At view line 6, the initial evaluation of `localStorage.getItem(KEY)` occurs inside `try`. The catch immediately evaluates `localStorage.getItem(KEY)` again as the right-hand side of `rejected=...`. If storage-object access or this read consistently throws, that second exception escapes the catch. Execution never reaches `game=new Camp(); blocked=true; paused=true;` in that same catch. The surrounding IIFE has no further exception boundary. The Journey/Export/Import handlers at lines 76–85, the storage/lifecycle handlers at line 86, and initial `ui`/frame setup at line 88 are therefore not installed or executed.

Disproof attempts: a parse error with readable storage is handled, and a transient error affecting only the first read would also allow the second read to succeed. Neither is the stated persistent-denial case. `save` at line 10 has its own guarded write, but it cannot guard bootstrap because it is not the caller and bootstrap never reaches it. `retainRaw` at line 5 does not help either: the first storage read precedes it. No source-level alternative recovery handler catches the second failure.

The impact should be described precisely. The game-specific scripted recovery controls remain inert, but ordinary HTML navigation links in the shell remain usable. This does not establish that the whole document or all browser controls stop working. The app does not reach its initial save, so this chain does not overwrite the existing durable KEY. It also cannot export bytes it was never allowed to read. An eventual honest blocked interface could explain the access problem, but the current code aborts before rendering that explanation.

**P-02 environmental confidence.** The concrete stronger platform hypothesis is denial while obtaining the storage object, for example under an origin or storage-access policy restriction; both references in line 6 reevaluate that access. A test that overrides only `Storage.prototype.getItem` demonstrates the exception-control-flow defect but is not by itself evidence that a particular supported browser naturally throws from that method for this HTTP origin. The source and candidate report do not identify an actually observed denial in the deployed top-level environment. They also do not establish that normal private browsing always denies reads, and I make no such claim. Persistent read denial is therefore a supported fault-handling scenario with a confirmed code consequence, while the precise real-browser configuration and its frequency remain unverified. A Spark fixture should label injected read/getter faults as fixtures and avoid presenting them as a measured production incidence.

The existing recovery helper at `tests/browser/hearth-rts-recovery.cjs:10` injects `setItem` failures and leaves reads working. Its write-quota coverage cannot disprove this separate bootstrap problem. Medium is appropriate for loss of the game's recovery interface when storage access is unavailable, without elevating it to saved-data destruction.

**P-03: distinguish raw presence from parsed truthiness.** View line 6 has two truthiness gates: `raw ? JSON.parse(raw) : null` and `state ? new Camp(state) : new Camp()`. For present raw text `null`, `false`, `0`, or `""`, the first gate parses valid JSON, and the second treats its falsy result as no saved camp. The engine validator is bypassed because the code invokes the no-argument constructor. `paused=!!state` is false, no version backup branch runs, and `blocked`/`rejected` retain their initial false/null values. Line 88 then invokes `save`; if storage writes succeed, line 10 replaces the original bytes with a fresh camp. There is no confirmation or rejected-save export in this path.

An actual absent key also yields null and intentionally takes the fresh-camp path. The bug is that present invalid values share that path. A raw zero-length string is an additional variant: the first truthiness gate skips parsing entirely. By contrast, a whitespace-only string triggers JSON parsing failure, and a truthy malformed object reaches `Camp` validation; those cases can enter the existing rejected-raw recovery path. Thus the candidate is not a claim that all invalid JSON is overwritten.

Disproof and origin limits: `Camp.serialize` serializes a camp object, so no ordinary successful app save is shown to produce these primitive payloads. The candidate requires preexisting invalid bytes, such as a deliberate fixture or some earlier external/corrupt write; this review establishes no natural browser mechanism that turns a valid camp into `false`, `0`, `null`, or an empty string. None of those values contains a legitimate playable camp. Therefore this is a Low inconsistency in the adopted fail-closed/raw-retention behavior, not loss of ordinary earned progress. The shell's statement that previous Hearth saves are preserved is principally about a different save slot and is not independent proof of a promise to preserve every malformed primitive in this slot. The retention requirement here comes from the stated rejected/corrupt-input recovery scope and its implementation for other bad payloads.

The export expression at line 77 is also truthiness-based (`rejected || game.serialize()`): if a future bootstrap change merely stores raw empty bytes in `rejected`, that particular value would still fall back to exporting the fresh camp. This does not alter the present startup proof; it narrows what a complete empty-byte retention result would have to demonstrate. The JSON text `""` itself contains two quote characters and is a truthy raw string, so it must not be confused with a genuinely zero-length stored string.
