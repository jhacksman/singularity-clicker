Verdict: confirmed, narrow Low status defect
Previously empty workers resume installation automatically, but their serialized
reason and displayed selected/card status remain "Waiting for site supplies"
until another start/order/completion transition replaces that reason. The material
and installation logic itself continues correctly. The scope supports Low rather
than a demonstrated Medium functional failure: no blocked completion, resource
loss, order loss, or invalid save follows from this status text alone.

Disproof attempted
The view independently derives the site's next action from live supply counters.
At view288, when no source-reserved or carried material remains, Next becomes
"Install the delivered materials." The work progress and onsite counters also
remain live. Thus a stronger claim that the entire inspector falsely says the
site cannot proceed is disproved. Those live site fields do not override the
individual worker status, however, and can contradict it in the same panel.

Exact source transition
1. engine220–222: when an active site has no reachable unpicked source choices,
   startSupply routes the empty worker to the site, sets phase='construct', and
   sets reason to "Waiting for site supplies" unless staged already equals the
   recipe. This is the expected waiting state while the last loads are carried.
2. engine462: an at-site construct worker with an incomplete staged recipe and
   no remaining source rows simply continues the tick. There is no reason update.
3. engine230–233: the final carrier unloads into staged, clears its cargo/tag,
   and calls start(u) only on ITSELF. Its own startSupply now writes
   "Installing outpost" (or workshop). Earlier waiters are not restarted here.
4. engine462: once staged equals the recipe, each earlier at-site construct worker
   falls through to b.work += dt. There is no assignment to u.reason and no start
   call on that path. Their old Waiting reason survives while they add real work.
5. engine240/462 eventually clears the completed site's orders through start(),
   replacing the stale reason. The mismatch can therefore last through the
   installation interval, rather than being only a single rendering frame.

Minimal status-only correction
At the already-authorized installation branch, after verifying a physical site
has its complete staged bill and immediately before adding that worker's dt,
refresh its reason to "Installing "+b.kind. Do not call start() on all workers:
that would unnecessarily reset work/path state and can affect manual successors.
Keep the existing order, phase, path, cargo, counters, work rate and ID unchanged.
Alternatively derive empty-worker installation status from current site state in
one shared view helper, but an engine reason refresh also keeps exported reasons
consistent. Root remains the sole owner of any future correction.

Bounded wording assessment
For the physical-v6 placement quote, "After delivery: 24 worker-seconds to
install." (32 for workshop) accurately names the unchanged installation bill.
It does not state a wall-clock completion ETA, include travel/hauling in that
number, promise all selected workers are continuously productive, or add a new

desktop path as well as touch confirmation. No timer, recipe, or order change is
needed. For legacy playable/prepaid placement, omit the physical-delivery prefix
and use "Installation: 24/32 worker-seconds" so the new text does not falsely
promise retroactive hauling in the compatibility path.
