G01 actor and eligibility oracle
waitingInstallers155–159 requires an active unfinished physical site and an
empty, unqueued Build actor already at its site edge with zero path, construct
phase and the original Waiting reason. readySiteDeliveries160–163 identifies
tagged carriers actually at the same site edge with zero remaining path.

materialStep276–287 requires real positive simulation time and work gain on an
active unfinished site. It determines which prior waiters should contribute by
combining staged material with only ready receipts whose carrier IDs sort before
that waiter. This matches the engine's stable sorted actor turns without using
the new Installing string as proof of eligibility. Each qualifying SAME actor
must retain Build(site), construct, empty hands, empty path, no successor and
the new Installing reason. Earlier final receipts can therefore fund later
workers in the same tick; lower-ID waiters before the final carrier are checked
on their next work tick.

The pre-existing exact fully-staged labor oracle remains at231–234. The G01
status checks supplement it; they do not replace its independent work-rate
arithmetic with the actor's status string.

G01 DOM and paired artifact evidence
installationStatusDOM164–173 selects the relevant worker IDs, inspects the site,
and runs the existing state-derived supplyText assertions. For every tracked
actor it requires the exact card small text, exact card title and the same named
worker/status in the site's Selected text. This matches the view's empty-worker
unitStatus/unitDetail behavior. It does NOT inspect the separate individual
worker inspector, and the report's ui array correctly limits the claimed scope.

captureWaitingInstallation174–188 captures a previous waiter only once the
currently staged goods plus at-edge ready deliveries can fund the exact recipe.
It records that actor's ID, site, scenario, time and before checkpoint after
asserting its Waiting DOM. Selection is restored afterward. On a zero-tick
sample, the same-time guard avoids duplicate before captures. If a final receipt
occurs after that waiter in actor order, the next iteration can capture the still
Waiting actor at the now fully staged boundary before its actual work tick.

The after witness292–298 requires the same scenario/site and that the recorded
actor is among the independently eligible installers. It also requires the
recorded before time to equal the exact before state of this transition. Thus an
old unrelated screenshot or the final carrier alone cannot satisfy the pair.
Both capture calls use ordinary Journey downloads, require the exported full
state to equal the observed state, take a full-page PNG and retain checkpoint
hashes. The resulting report points to both checkpoint files and names the
tracked actor. Those entries in turn bind raw JSON and PNG bytes.

Selection/inspection clicks change UI state while paused; neither issues a work
order. restoreSelection preserves the prior selected IDs, including the empty
selection case, and the code re-inspects the current site afterward. Exact
capture-state equality would detect an unexpected game-state change during
observation. No new synthetic camp, direct engine call, state grant or storage
seed is added to the ordinary journey.
