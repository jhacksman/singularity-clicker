## Confirmed critic findings and attempted disproof

Neither is true in the baseline. Core `naturalResidue()` reads the current engine and replaces only the clamp (`tests/hearth-rts.test.cjs:62-74`); the browser control similarly replaces only the clamp in the current built HTML (`tests/browser/hearth-rts-roundtrip.cjs:5-9`). After a version bump, both controls therefore produce v4. Bootstrap immediately requires repair of that exported control (`tests/browser/hearth-rts-bootstrap.cjs:6-7`), while `repairWorkResidue` explicitly accepts only versions 1/2/3 (`engine.js:51-61`). Its later export/main-save assertions compare against the pre-migration repaired object (`bootstrap.cjs:58-59,70`). Changing the outer version to4 makes those assertions materially different.

The appropriate correction is already in the root plan: leave v4 negative-work states rejected, keep the v4 old-subtraction proof, and supply an independently identified legacy-v3 repair fixture. A pinned historical source is stronger provenance; an explicitly labelled version/schema projection is acceptable compatibility evidence but must not be called an unmodified historical artifact. Assert exact raw legacy retention separately from the expected migrated v4 world. Retain a direct v4-negative-work rejection test even when ordinary future-version fixtures move from4 to5. I do not classify this as demonstrated production cargo loss: it is an actual dependency in the tests which must be resolved before a trustworthy green run.

**P2, Low policy discrepancy: confirmed and resolved.** Custody section2 says to reset extraction progress, while the engine proposal preserves it. The root now selects exact preservation during acceptance, travel and holding, followed by existing reset behavior when ordinary work subsequently starts. This is internally consistent because carryMove has no extraction branch. `start()` resets work (`engine.js:153`), so direct installation/arrival must avoid it. Paid construction and knapping work live on their projects and are a separate invariant. No additional product finding follows from the now-superseded proposal wording.

## Custody and admission stress review

1. **Picked-up cargo remains one owned quantity.** `releaseTransfer` reads order/next and cancels only a positive pending share (`engine.js:129`). A valid marked carrier already has pending0 and matching job/resource membership (`:41-47`). Keeping the marker and quantity, while deleting routing intent/dropoff, therefore leaves the transfer partition intact. `pruneTransfers` already retains any job referenced by a marker (`:131`). I found no need for an additional carried-quantity field or a cancellation counter for picked-up goods. Either would create another place for custody to diverge.

2. **Queued pickup and actual cargo must remain distinct.** A gathered wood carrier may have a future stone transfer in `next`. Releasing that share before clearing order/next releases stone availability without refunding stock, retyping the wood, or marking wood as transferred. Uneven 5+1 allocations and one loaded/one pending peer are necessary tests because equal full loads can conceal per-actor cancellation mistakes. The proposed sequencing covers this; no code yet demonstrates it.

3. **Whole-group admission is plausible but must survive the actual implementation.** Engine `command` preflights all changing actors (`:173`); view formation dispatch preflights all destinations before its synchronous per-actor calls (`view.js:60-64`). Movement does not itself change static geometry. Preparing routes before releasing shares, and introducing no later fallible gate, can preserve atomicity. I could not establish a current plan contradiction here. Required rejection comparisons must include the complete serialization, not only physical totals: paths, work, reasons, old queues, pending shares and IDs can be corrupted with conserved stock.

4. **Stop cannot be deduplicated as already idle while a load is held.** Baseline dedup checks `next || order`; baseline loaded commands call home (`:173-174`). An idle held load and a migrated returning actor with next=Move are the two distinct traps. The plan handles both: held Stop initiates physical return, and a newly issued Move supersedes a legacy queued Move immediately. Active same-target Move alone is a no-op. The engine proposal explicitly allows a post-arrival same-tile Move to accept and hold on the next tick; repeated-command exact-state comparisons should therefore cover the active interval, rather than silently imposing no-op behavior after arrival.

5. **Receipt must not replay a stale Move.** `receive` can retain the current order and call `start()` after clearing cargo (`:138`). Clearing the old manual Move identity before Stop/new-work return is essential; simply setting phase return is insufficient. The plan explicitly covers this. Verify beyond the receipt tick so a latent old Move/gather/transfer cannot pass a first-return-only oracle. A subsequent new transfer requested for a gathered carrier should also follow the general accepted replacement rule; it is not permission to adopt that gathered load as the new transfer lot.

6. **Duplicate Send does not authorize return to an old route.** `activeTransfer` recognizes the retained marker (`:106`), and duplicate `transfer()` currently returns the old job without commanding it (`:124`). Thus retaining ownership does not itself cause movement. The necessary UI correction is accurately planned: distinguish an unchanged existing obligation from resumed delivery, and describe moving versus holding actors truthfully. Another carrier's ongoing job must not be described as globally paused.

## Path, saved-state and replay stress review

The dedicated phase preserves the prior F6 boundary: ordinary walk/extract/construct/craft/pickup must still reject marked transfer cargo. carryMove receives a narrow permitted shape and only movement/holding behavior. Simply adding it to a broad phase enum would not establish the plan's proof. Unknown/forged combinations must be rejected independently: wrong order, next/dropoff, empty load, marker/resource mismatch, pending ownership, bad route tail, noninteger/blocked/disconnected nodes and empty route before arrival.

The root's cardinal-node and first-node constraints close an ambiguity in the earlier phrase "ordinary legal path." The baseline grid pathfinder rounds the actor's start (`engine.js:145-147`). A fractional actor with the target equal to that rounded cell can receive path[] despite not being physically there. The proposed one-node connector preserves the existing grid model and finite speed. Generic movement also shifts a node early using `d <= step + .00001` (`:196`); carryMove must set coordinates exactly only when the distance is actually within the tick budget. The critic's near-one-cell `.333332` case is a sound boundary to cover statically; I did not execute it.

I tried to find an unavoidable mismatch between route validation and normal motion. Along the proposed grid segments, the first unconsumed node remains the rounded current cell or its cardinal neighbor, and integer remaining nodes retain cardinal adjacency. A same-rounded-cell connector likewise stays within that cell while approaching its exact integer endpoint. This supports the proposed validation shape; it is not a proof of arbitrary collision geometry, which is explicitly outside scope.

`build()` currently reroutes all loaded paths home (`:187`). The plan correctly requires carryMove priority before that branch, retaining the named target, work and custody on both successful replan and safe hold. The zero-path exact-arrival boundary does not by itself prove a missed-build-reroute defect: existing placement rejects building over an occupied target (`:182`). Actual implementation must still be inspected. A blocked held state intentionally has idle phase, the retained Move target and no path, so applying the active-route reachability checks to it would cause another reload failure. Canceling the obstruction must not restart the held Move without a new command.

Saved snapshots and replay should include command acceptance, fractional movement, just before/after the last node, exact arrived-but-not-yet-held boundary if retained, held arrival, blocked hold, and Stop/receipt. Strict validity at each tick plus exact continuation of an uninterrupted/restored pair is stronger than accepting only a final held save. Wait beside a store through multiple ticks to disprove implicit receipt. Check typed physical totals, job partitions, worker work and unrelated paid-project progress independently.

## Migration and UI boundaries

The outer v4 barrier is justified. Baseline `valid()` rejects unrecognized top-level versions before unit processing (`engine.js:19`); old v3 readers therefore reject all v4 states consistently, rather than accepting some held states and misinterpreting active ones. Update exact version===3 transfer-order/phase guards (`:28-29`) while keeping storage schema1. Keep the constructor's storage-adoption cutoff `<3` (`:64`): widening it would rebuild valid v3 storage/jobs at the hearth. Preserve post-migration full validation, including rejection of old states whose adoption cannot produce a valid current world; do not turn that failure into a fresh camp or destructive save.

Existing bootstrap/import code already retains source before the main overwrite and adopts imports after successful persistence (`view.js:10-22,253-258`). Add v4 retention families without removing the older or residue families. Byte identity applies to backups; current migrated state may differ by the outer schema and existing deterministic normalization. Backup collision, backup-read/write failure and main-write failure need separate assertions. A repairable v3 source must keep its exact defective bytes even though its adopted v4 state is repaired. A new v4 negative-work source must remain rejected and exportable, not repaired to satisfy the old fixture.

The UI plan correctly narrows return-first feedback: Move carries now and holds on arrival; Stop physically returns; Gather/Build/Craft remain return-first in this bounded increment. It also distinguishes paused planning, active travel, holding, blocked return and transfer provenance. Merely updating the toast is insufficient: portraits, inspector and incoming counts must agree. Clearing dropoff removes the existing store incoming promise (`engine.js:77`); the UI must not edit quantities to achieve that appearance. Engine evidence must be paired with real M/button/touch/contextual input and live export checkpoints on Spark. Headless input does not establish physical-touch usability or human understanding.

No additional confirmed plan blocker remains after the root's P1/P2 resolutions and route clarification. Concrete implementation review and exact-commit Spark evidence remain required.
