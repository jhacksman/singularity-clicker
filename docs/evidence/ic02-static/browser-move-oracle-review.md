## BM-O1 — Medium: transfer Move can pass after command-time teleportation

Lines 123-127 inspect the loaded transfer, issue the button Move, check cargo/provenance/storage, observe exactly one simulation tick, and eventually check held target coordinates. Unlike the gathered-load branch at lines 88-95, they never compare accepted x/y/work against the pre-command carrier and never require first-tick displacement along the accepted route. There is also no explicit target order, next, or path comparison in that branch, although the current validator constrains some of these indirectly.

Concrete false-pass counterexample: for a marked carrier only, a faulty Move transition sets its coordinates directly to `(2,3)`, installs `order=Move(2,3)`, `phase=carryMove`, `path=[]`, `next=null`, deletes dropoff and retains cargo/resource/work/marker/storage. This is a valid exact-arrival carryMove shape under the proposed/current validator. Acceptance checks pass. The next `.1` tick changes it to idle holding without movement; line 126 checks only cargo, marker and custody, so it passes. `until` immediately accepts idle arrival at the already-teleported target. Reload, duplicate Send and later Stop can all behave correctly and satisfy the remaining assertions. A one-tick delay before beginning an otherwise valid transfer Move is also undetected.

Minimal correction direction: give the transfer branch the same before/accepted position and work checks as the gathered branch, explicitly inspect Move order/next/path, and assert the exact first `.1`-tick displacement with load/type/marker preserved. Confirm the fixture starts physically away from its target. This requires assertions, not changing its earned seed or exposing engine internals in the page.

## BM-O2 — Medium: transfer settlement does not prove receiver or physical return

Lines 132-134 click Stop and then wait only for the old job to disappear and all cargo to become empty. They check unchanged gathered-production counters, aggregate typed totals and the total transferred counter. The message says the diverted western load returns to source storage, but no assertion checks that source's balance, the outpost's balance, accepted return position/path/dropoff, or the carrier's receipt position.

Concrete false-pass counterexample A: after otherwise correct Move/hold, Stop remotely credits the held five stone to the hearth, clears the marker/cargo, counts five recovered and prunes when peers finish. Global material and the expected fifteen transferred stone remain correct, so the test passes without any physical return. Counterexample B: the carrier returns normally, but faulty receipt credits those five stone to the outpost while still classifying them as recovered. The source/outpost balances are wrong, but total stock, transferred count, unchanged gathered production and final strict validity can all pass after the job is pruned. The validator does not retain a historical receipt ledger that can recover this missing observation.

The final arithmetic itself is reasonable for the intended fixture: the main browser creates a four-worker, twenty-stone hearth-to-outpost job, and the selected carried share is removed from the amount expected to become delivered. The error is treating that aggregate equality as proof of the named receiver and physical settlement.

Minimal correction direction: export immediately after Stop, check unchanged physical position/load/marker and a real return route/dropoff; observe return movement and actual receipt location; check both store balances against the earned initial allocation. Isolate peer obligations when calculating expected changes. At minimum preserve evidence immediately before the carrier's receipt, since terminal pruning deliberately removes the per-job delivered/recovered fields. Aggregate conservation remains necessary but is not sufficient.

## BM-O3 — Medium evidence gap: following the application's path does not independently exclude a home detour

The gathered-load branch requires a legal carryMove whose path ends at the target (lines 88-90), then computes expected first movement from that same accepted `u.path[0]` (93-95). This proves movement follows the exported route at the expected speed. It does not independently establish that the accepted route lacks the prohibited automatic home leg.

Concrete false-pass counterexample: install a clear cardinal route from the gathered worker to a hearth edge, back along connected clear cells, and onward to `(2,3)`, retaining carryMove/cargo throughout and never receiving at the hearth. Such a route can satisfy the validator's node connectivity, first-node and target-tail constraints; those checks do not prohibit revisiting cells. It is short enough for this fixture's arrival budget. The test derives its first-step expectation from the detour, so it passes that assertion, later reaches the target holding the same cargo, and passes all conservation/reload/Stop checks. The pinned old-page control rejects the old `return + next=Move` representation, but does not rule out a home waypoint concealed inside the new phase.

Minimal correction direction: use an independently justified target-bound route/first-leg witness for this known clear-region fixture, with a precondition that distinguishes it from the old home route. A simple explicit clear corridor or independently checked path-length bound can provide that witness. Do not impose a general rule that Euclidean distance must decrease every tick; legitimate obstacle routing can move away from its final target. This is a gap in the claimed no-home-detour evidence, not a claim that the inspected movePath implementation currently adds such a detour.

## Scope and execution limits

`tick(500)` and `tick(3000)` validate each observed checkpoint, not every internal `.1` simulation tick. The first-step helper observes exactly one tick; longer polling can skip transient invalid states. Per-tick engine validity/replay tests remain necessary. This browser file tests held reload, not moving/blocked/returning reload continuation, mid-segment redirect, same-rounded-cell arrival, paid-building reroute, Stop-with-no-route, uneven pending cancellation, work reassignment or mixed actor admission. Those planned cases need their separate evidence; they cannot be inferred from this PASS string.

The four input methods are tested with gathered cargo; the transfer case uses the Move button. All current command feedback observations are made while paused. This does not independently verify every running-state portrait/inspector phrase, a visible zero-incoming store total, or the full cross-product of inputs and cargo origins.

Fixture setup and cleanup can still fail on Spark because of viewport actionability, clocks, browser support or server startup. The map hit precondition makes overlays fail visibly instead of silently sending a different action. I found no source-supported inevitable actionability or export race in the current helpers. Reports retain completed groups and a failure summary, but assertions performed after `close()` may lack a usable page for a failure screenshot; this is a diagnostic limitation, not a false pass.

No source-fix closure, execution result, full IC02 completion, navigation integration or publication approval is claimed. BM-O1/O2/O3 require the coordinator's fresh skeptical gate before the sole fixer changes the harness.
