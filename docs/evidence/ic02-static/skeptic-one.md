## IC02-P1: confirmed, with limited scope

I attempted to disprove the conflict by checking whether the negative control pins an old engine or overrides the saved schema. It does neither:

- `tests/browser/hearth-rts-roundtrip.cjs:6–9` loads the current built HTML and replaces only the extraction remainder assignment. Its starting artifact is the current journey's earned camp (`:5,17`), and the generated negative checkpoint is written unchanged (`:38–41`). After the planned engine bump, this is a v4 checkpoint.
- `tests/browser/hearth-rts-bootstrap.cjs:6–7` immediately passes that checkpoint into `repairWorkResidue` and asserts a non-null valid result. Existing `engine.js:52` restricts repair to v1/v2/v3. Preserving that intentional bound means these unchanged tests fail before the browser recovery scenarios begin.
- The unit helper has the same dependency: `tests/hearth-rts.test.cjs:65–67` reads and minimally modifies the current engine, `:68–75` generates its current-schema checkpoint, and `:82–83` requires repair success on that unprojected object.
- Even after supplying a proper legacy fixture, bootstrap `:58–59,70` directly compares the adopted/exported state with the pre-constructor repaired object. Correct construction upgrades that legacy object's outer version to v4, so those equalities need a separately expected migration result. Core migration `:91` also explicitly expects version3 and must follow the new outer version.

Thus this is not speculative. Leaving the tests unchanged conflicts with the chosen strict v4 recovery policy. Conversely, it does **not** justify extending the repair helper to v4 or alleging that `carryMove` itself loses cargo. A negative checkpoint generated by intentionally reverting the clamp in a current v4 test build is a regression control, not evidence that v4 needs automatic repair in production.

The root's current `transition-plan.txt:121–128` supplies the correct resolution: keep known-generation repair bounded; separate the current-v4 negative control from a pinned/generated legacy-v3 recovery fixture or an explicitly labelled schema projection; compare adopted worlds after normal migration. This closes the design ambiguity. Concrete fixture provenance and changed assertions remain implementation/evidence obligations, not an unresolved reason to reject the overall transition design.

For a projected fixture, preserve both the unmodified generated artifact and the derived compatibility input, label the projection, and do not describe derived bytes as a historical browser save. For a pinned v3 fixture, record its generating source identity. In either case, assert exact retained legacy bytes and independently expected current state. Do not simply derive every expected value by calling the same constructor under test; separately assert preserved stores, transfer jobs, reservations, cargo, queued orders, paid progress and the deliberate outer-version change.

Keep two distinct version tests: unknown future payloads move to v5; a known-v4 payload with negative work must still fail strict admission and return no repair. Blindly changing every test literal `version=4` to `5` would erase the latter oracle.

## IC02-P2: resolved policy; no remaining defect

The custody proposal's reset sentence disagrees with the engine proposal, but root explicitly chose preservation of the exact nonnegative unit work remainder through Move and held arrival. A later ordinary work start retains its existing reset behavior. That instruction supersedes the older reset sentence.

## Transition-safety challenges and why they do not defeat the plan

**Transfer custody and held arrival.** Replacing an order could appear to orphan the transfer job, but existing `pruneTransfers()` already retains any job referenced by `u.transfer` (`engine.js:131`). Preserving that marker, resource and amount is sufficient to retain physical custody while the movement intent changes. The plan correctly releases only positive unpicked allocations before replacing old order/next; `releaseTransfer()` reads both old fields (`:129`). Cancelling marked cargo itself would be wrong, and the plan explicitly forbids it. No new material ledger is needed merely for this Move slice.

**Unsolicited deposit beside a store.** Existing receipt is phase-driven (`engine.js:198`), not proximity-driven. A dedicated `carryMove` branch followed by held idle, with no dropoff and no call to receive/home/start, can therefore reach a store edge without depositing. The proposal's arrival transition has the necessary distinction. Test the final-node boundary and several later ticks, because observing only the initial direction would not prove arrival behavior.

**Stop and subsequent work.** Keeping the Move order during return could restart it when `receive()` calls `start()` (`engine.js:138`). The plan explicitly replaces that identity and clears the queued Move before Stop/work settlement. Stop on idle-held cargo must remain an accepted return request despite order already being idle; the proposal addresses that duplicate trap. Repeated Stop after return has started should not reset custody or refund twice. These are concrete required tests, not newly uncovered plan omissions.

**Legacy queued Move and duplicate Send.** Existing command deduplication checks `u.next || u.order` (`engine.js:173`), so preserving that code verbatim would wrongly suppress a fresh Move matching an old queued destination. The plan explicitly distinguishes executing versus queued Move and preserves the old plan only during migration. Existing duplicate transfer returns its old job without issuing command (`:124`), so retaining custody does not inherently resume it. The UI must accurately describe that unchanged obligation, as its plan already requires.

**Build rerouting.** Existing build routes loaded actors home (`engine.js:187`); merely changing command admission would fail. The proposed earlier `carryMove` branch, same-target replanning and safe idle hold cover this call site. Blocked hold retains `order=Move`, cargo/work and empty path and must remain loadable even though the destination has become blocked. Applying active-route endpoint rules indiscriminately to that idle state would create a new reload failure; the critic already separates them. Cancellation of the obstructing site must not autonomously restart the held order.

**Fractional position and arrival.** Existing pathfinding rounds its starting cell, and generic tick can pop a path node before exact arrival (`engine.js:145–147,196`). The plan's final connector and exact reached-node handling address the specific empty-path-at-fractional-position conflict. The route helper must retain the existing movement budget, without snapping over an unreached segment. Round-trip immediately after acceptance, at fractional positions, on the last-node tick and on the following hold tick is necessary to demonstrate this, not a reason to claim a plan-level conservation defect now.

**Validator and schema boundary.** Version4 plus a dedicated phase prevents an old v3 reader from treating new movement as an old return/walk state. Restricting marked transfer cargo in ordinary work/pickup/walk still preserves the F6 boundary. New active-route validation must enforce the planned integer/in-bounds/unblocked nodes and exact target tail; generated-route and forged-route tests should establish the precise meaning of the promised legal path. No transition quantity may be repaired or invented to satisfy that validator.

**Migration.** The storage reconstruction cutoff must remain `<3` (`engine.js:64–70`); changing it to `<4` would erase real v3 local custody. The root and engine plans explicitly retain `<3` and change only the outer schema for v3. Old queued return plans are not silently converted into immediate Move. Exact raw backup-before-adoption for startup/import remains necessary, including failures and distinct-byte collisions. These are essential implementation gates already in the plan.
