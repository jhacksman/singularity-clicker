IC02 UI changes proposed for the later authorized implementation

1. Command help and dispatch feedback

Current view.js:40 applies returnNote(workers) to every dispatch, and :62-66
therefore promises a store detour even for Move. Replace this with verb-aware
feedback. Capture the relevant pre-command cargo/intent, but report acceptance
only after command succeeds. Reuse one derived description for mouse, M, touch
Move and unambiguous contextual ground Move. Keep Gather/Build/Craft contextual
targets and the current all-selected formation preflight.

Suggested visible copy (quantities/resources come from actual selected actors):
- Move mode: "Move: choose clear, reachable ground. Carried goods move with the
  villager and stay with them on arrival." Retain blocked deposit/building help.
- Running gathered load: "Move with 3 wood · hold the load on arrival."
- Paused gathered load: "Move planned with 3 wood · starts on Resume."
- Running transfer load: "Move with 5 wood · this carrier's delivery is paused."
  The pause concerns this actor's old delivery route, not the entire transfer job
  or the simulation. If paused, use "Move planned … starts on Resume" first.
- Mixed selection: "Move assigned · N villagers · carried loads stay with their
  carriers." Do not fabricate one combined resource or say every actor has cargo.
- Same active destination: "Already moving to this destination" (or "This Move
  is already planned" while paused). No new acceptance, path reset or cargo action.
- Invalid group target: retain the specific rejection reason and add "Previous
  orders kept." Every selected actor, queued share, cargo and paid job must remain
  unchanged; no success flash after a partial application.

Move on a live deposit/building remains invalid; exhausted clear ground can be
accepted when the engine admits it. Formation targets must all be validated
before commands. Newly issuing the same destination as an old saved next=Move
must redirect immediately; a legacy queued Move is not an active duplicate.
After arrival, same-tile Move must never imply deposit or resume old work.

2. Visible actions and persistent explanation

Keep the existing #move, #stop and armed targeting controls. Prefer the visible
Stop label "Stop and Return", retaining S and "return cargo". Empty Stop still
stops the current order; loaded Stop explicitly returns goods to a reachable
eligible store and then idles. Preserve Stop's existing enabled-when-unblocked
readiness behavior. No new general Hold button or Resume transfer is implied.

Replace shell.html's universal #cargo-command-note with a short truthful rule:
"Move carries goods and holds them on arrival. Stop returns goods. New work
orders still return carried goods first."
This last sentence deliberately discloses the deferred work-switch behavior.
Existing placement/knapping return-first copy should remain accurate. Loaded
Gather/Build/Craft dispatch continues to disclose its return-first sequence.

Stop feedback must not promise the original transfer receiver or instant credit:
- accepted return: "Stop and Return · carrying 5 wood to reachable storage";
- paused: "Return planned · starts on Resume";
- no route: "Holding 5 wood · no reachable store. Move to another location or
  try Stop and Return when a route opens."
Use the actual engine result/status; do not show the accepted-return sentence
when home() failed. Repeated active Stop must not reset/recredit; Stop on an idle
actor holding cargo must still request a physical return.

3. Portraits, inspector and economy

Current view.js:229 hides the action of a loaded non-idle actor behind a bare
quantity. Derive a compact next-action label from state, with the engine's reason
available in the inspector/title:
- carryMove: "Moving · 5 wood"; paused presentation: "Move planned · 5 wood";
- arrival idle with cargo: "Holding · 5 wood";
- return: "Returning · 5 wood"; distinguish an active transfer delivery if useful;
- blocked manual Move: "Move blocked · holding 5 wood".
Do not mislabel an extractor with cargo as returning; use its actual phase.
The inspector should avoid repeating "carrying" when the reason already includes
the amount. Arrival copy: "Holding 5 wood. Choose Move or Stop and Return."
The persistent action tray supplies those actual controls, including touch.

For a loaded transfer actor, add concise custody context when inspected:
"This load belongs to the transfer from [source] to [assigned receiver]. Its
delivery is paused for this villager. Stop and Return uses reachable storage."
Resolve names by stable IDs; do not imply that another actor's delivery stopped.
Source-to-receiver context is provenance, not a guarantee that Stop selects that
receiver. A receipt elsewhere is recovery, not new gathered production.

Keep economy().inTransit labelled "Carried": it includes motionless held cargo.
Keep held villagers in the idle count unless a separately reviewed change says
otherwise; a tooltip/helper may clarify "Idle includes villagers holding goods."
Do not classify them as empty/free. Clearing dropoff in the engine must remove
their old store incoming promise immediately; no UI-side stock adjustment.

4. Existing transfer button edge case

activeTransfer/quoteTransfer can return the original job ID while a manually
moved/held carrier still owns its load. Current storeUI (:210-212) reports
"Transfer assigned" even when that repeated request does not change movement.
The new UI must not claim this resumes delivery. Prefer an explicit unchanged
result from the engine, or derive the existing job/actor status without mutation:
"Transfer already exists · selected carrier is holding its load. Use Move or
Stop and Return." Keep other active carriers accurately described. It is safe
to disable that duplicate action with this explanation; do not clear ownership,
reserve another lot, or add an unimplemented Resume action. A repeated old Send
must not silently reclaim a manually moving/held carrier.

5. UI evidence required on Spark after implementation

Use real earned gathered and transfer loads, then actual M/button/touch target
input. Observe the first running displacement, actual route, exact held amount,
arrival and continued idle holding. While paused, confirm planning copy and no
movement until Resume. A store-edge Move must not deposit. Show visible status
and actions in portrait/inspector/tray, not just internal engine assertions.
Repeat Move, redirect mid-segment, Stop during/after Move, Stop with no reachable
store, mixed-group rejection, and a building-induced blocked/replanned route.
Check no stale incoming; physical receipt alone changes the appropriate counter.
Exercise duplicate Send while moving/holding, preserving custody and other
carriers. Roundtrip moving/held/blocked/returning states with exact raw backups.
Preserve UX023 keyboard ownership, touch confirmation, map pan/hit testing and
preventScroll focus behavior; avoid unrelated changes to those input systems.
Use an immutable old-behavior negative control showing the former home detour
from the same earned load. No physical-touch/human-prediction claim from headless
input. Engine proof plus browser proof are both required for this Move slice.

validateRTS on a clone, but its browser default is merely HearthRTS.valid. The
destination first applies repairWorkResidue, then constructs Camp, including
legacy migration and strict postvalidation (RTS view.js:16; engine.js:49-64).

alone does not establish a successful post-migration destination state.

retention/repair/adoption stays destination-owned. If the helper represents
