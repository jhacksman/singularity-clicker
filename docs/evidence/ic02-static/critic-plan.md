## Verdict

The dedicated v4 `carryMove` design is a sound bounded direction, subject to the guards below and the required fresh skeptical reviews. I found one Medium evidence/design blocker (IC02-P1), already acknowledged by root, and one low-risk policy inconsistency (IC02-P2), now explicitly resolved by root's decision recorded below. I did not find an unaddressed High conservation failure in the proposed transitions. This is permission to continue design scrutiny, not source or runtime closure.

## IC02-P1 — Medium: version bump invalidates the residue-recovery evidence chain

The engine proposal correctly keeps `repairWorkResidue` limited to known defective v1/v2/v3 generations. Root's integration plan says to update its supported versions, which must not mean admitting v4 negative work merely to retain the current tests.

Concrete dependency: `tests/browser/hearth-rts-roundtrip.cjs` replaces only the extraction subtraction in the new built application and exports its generated negative checkpoint. With a v4 engine, that checkpoint is naturally v4. `tests/browser/hearth-rts-bootstrap.cjs:6` immediately passes that checkpoint to `repairWorkResidue` and requires success. Core `naturalResidue()` and its explicit-repair tests have the same coupling (`tests/hearth-rts.test.cjs:62–107`). Leaving the tests unchanged either makes the suite fail or pressures the implementation to broaden recovery incorrectly. The bootstrap success/export assertions additionally compare persisted state directly with the pre-migration repaired object; a correctly repaired v3 object becomes v4 on construction, so those equalities must change deliberately.

Required resolution: keep strict v4 rejection of negative work. Separate the v4 subtraction negative control from legacy repair fixtures. Prefer an immutable/generated legacy-v3 checkpoint with source provenance; a controlled schema projection is acceptable only if explicitly labelled as a projected compatibility fixture, not an unmodified historical browser artifact. Assert raw legacy bytes stay exact; compare the adopted world against a separately expected normal migration, retaining all custody and progress fields. Keep a direct regression that v4 negative work is rejected rather than repaired. Root acknowledged this resolution before implementation; concrete fixtures and source remain unverified.

## IC02-P2 — Low, resolved at design stage: extraction-remainder policy differs between proposals

The custody proposal says a loaded Move resets worker extraction progress. The engine proposal explicitly preserves the nonnegative `u.work` remainder through Move and held arrival and avoids `start()` for that reason. Root currently leaves the policy open. This remainder is not a material quantity or paid job progress, so the discrepancy alone is not a duplication/loss exploit. Nevertheless it changes exact-save and repeated-command oracles.

Root explicitly selected the engine's preservation policy after this report was drafted: command acceptance, movement and held arrival preserve the exact nonnegative worker remainder; a later ordinary work start follows its existing reset semantics. I agree this is coherent because carryMove cannot extract. This decision supersedes the custody proposal's reset sentence. Tests must distinguish the worker remainder from building/knapping work, which remains owned by and preserved at its paid job. Do not reset it accidentally through generic `start()` while claiming exact state preservation. Source and test implementation remain pending.

## Concrete transition hazards and proposed guards

These are source-supported implementation traps already covered by the inspected proposals, not additional defects in an implemented patch.

The proposed accounting remains coherent: for each typed resource, stored + carried + deposit + spent stays constant; reservations remain subsets of stock. Every transfer retains `amount = remaining + delivered + recovered + cancelled + marked cargo`, and remaining equals pending shares. Manual Move changes no matter or receipt counters. Stop later makes an actual receipt: original receiver increments transfer delivery, another store increments recovery, and neither is gathered production. Gather-origin cargo retains no transfer marker and is credited as production only at its eventual receipt.

Atomic admission must remain real. The existing engine preflights all changing actors; the UI preflights the whole formation before synchronous per-actor commits. Prepared Move routes must not introduce a second fallible admission step after an earlier actor has released custody. Compare complete serialized state for rejected mixed groups, including paths, reasons, next/dropoff, IDs and reservations. Comparing just stock totals misses partial control changes.

Root additionally requires active carryMove routes to reject blocked endpoints/path nodes. Keep that check scoped to the new v4 phase. Require integer in-bounds route nodes before applying the current grid obstacle rules; generic `point()` permits fractions and `water()` uses integer equality. Generated grid routes and the proposed final connector have integer nodes. Preserve the exact-tail/arrival check. A blocked replan deliberately becomes `phase=idle`, `order=Move`, `path=[]`, retaining cargo and target; it must remain loadable without demanding that the now-blocked target or an empty active route be valid. This guard must not retroactively reject legitimate old queued-return states or idle held cargo.

## Evidence required for eventual closure

Spark, on the final immutable source, must cover genuinely earned gathered and transfer loads at command acceptance, first movement, mid-segment redirect, final node, held arrival, held reload, Stop return and receipt. Include a destination beside a store and wait long enough to disprove unsolicited receipt or work restart. Check typed totals and transfer partitions each tick; compare exact uninterrupted/restored continuation.

Exercise pending-only, loaded-plus-pending peers, gathered cargo with queued transfer, repeated same Move on every tick, same-target legacy queued Move, same-tile/fractional Move, invalid mixed selection, build-triggered reroute and blocked hold. Test Stop during movement and while idle holding, including an unavailable return route; distinguish active delivery from manually held custody when repeating Send. Preserve the existing Stop/work return-first tests while updating only the superseded Move expectations.

Use actual M, Move button/touch and contextual ground input, with visible next-action/custody text and paused planning. A previous-behavior control must use the same earned load and demonstrate the old home detour; it must not be a fabricated new-state shortcut. Browser automation cannot establish human prediction or physical-touch usability.

Migration evidence must include v3 pending and loaded transfers and queued return plans, v1/v2 adoption, exact raw v3 backup before v4 replacement, distinct collision retention, backup/main-write failures, v4 reload and rejection by the immutable v3 reader, and v5 rejection. Preserve the old residue-recovery evidence separately per IC02-P1. Later navigation support needs its own assembled evidence; its older isolated pass does not cover v4.

No runtime pass, source fix closure, full IC02 completion, capacity behavior, exporter completeness or publication approval is claimed by this report.
